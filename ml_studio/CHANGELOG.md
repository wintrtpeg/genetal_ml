## 24차 — "이거 진짜 돌려도 되나" 에 대한 답

정당한 질문이었다. 최근 몇 판이 계속 "내보내고 → 깨지고 → 고치고" 였고,
이번 버전에는 **파일을 영구 삭제하는 기능**이 새로 들어 있다.
답하기 전에 실제 위험을 따져 보니 진짜 구멍이 두 개 나왔다.

### 구멍 1 — 처음 켜자마자 예전 결과가 지워진다

정리 기준(최신 10개 · 2,000MB)은 이 기능이 붙기 **전에** 만든 결과물에도
그대로 적용된다. 사용자는 기준이 생긴 줄도 모르는데 새 버전을 처음 켜는
순간 오래된 실행이 말없이 영구 삭제된다. 그건 배신이다.

**첫 실행은 지우지 않고 알리기만 한다.** 찌꺼기는 그냥 치우고(잃을 것이 없다),
실행 결과는 "이런 게 기준에 걸립니다, 남길 것은 보관 지정하세요" 로 끝낸다.
한 번 미룬다고 디스크가 넘치지 않는다.

#### 첫 판은 유예가 3초였다

시연해 보고 알았다. 시작 정리가 알리며 표식을 찍고, **같은 실행의 종료 정리**가
그 표식을 보고 바로 지워 버렸다. 알림을 읽을 틈도 없다.

표식의 시각이 **이 프로세스가 시작하기 전**일 때만 삭제를 허용하도록 고쳤다.
같은 실행 안에서는 몇 번을 불러도 지우지 않고, 다음 실행부터 적용된다.

## 23차 — 회사 PC 4실패 · 전부 정리 기능에서 나왔다

환경 점검 36통과 0실패, end-to-end 통과, SHAP 정상. **제품은 멀쩡했다.**
실패 4건은 전부 22차에 넣은 정리 기능 주변이고, 셋 다 다른 문제였다.

### 1. 표시 때문에 삭제가 실패했다

```
ValueError: 'C:\Users\jpil.hwang\...\runs\run_1' is not in the subpath of
            'C:\Users\JPIL~1.HWA\...'
```

윈도우 `%TEMP%` 가 **8.3 단축이름**(`JPIL~1.HWA`)으로 잡혀 있으면 resolve 한
경로는 긴 이름(`jpil.hwang`)이 되어 표기가 어긋난다. 그래서 보고용
`relative_to` 가 ValueError 를 던졌는데, `except (OSError, UnsafePath)` 는
그걸 안 잡아서 **정리 전체가 중단**됐다.

"어떻게 보여줄까" 의 문제가 "지우지 못함" 이 되면 안 된다. `_show()` 로 감싸
어긋나면 전체 경로를 그대로 쓰고, 예외 목록에 ValueError 를 넣었다.

### 2. 회귀 테스트가 6분 → 30분

`find_junk()` 가 `ROOT.rglob("__pycache__")` 를 썼다. 결과에서 `.venv` 를
걸러 내긴 하지만 **`.venv` 안을 다 들어갔다 나온다.** 회사 PC 의 가상환경에는
파일이 수만 개고, 정리는 실행할 때마다 도는 기능이다.

rglob 대신 직접 걸어 내려가며 `.venv` · `.git` · `site-packages` 등에서
**가지치기**한다. 흉내 낸 환경에서 181배 빨라졌고, 회귀 테스트는 45초로 돌아왔다.

### 3. 내 테스트가 제품과 다른 조건이었다

fixture 가 `tempfile.mkdtemp()` 를 그대로 썼다. 제품의 `ROOT` 는 임포트 시점에
`resolve()` 되므로, 테스트도 같은 모양이어야 같은 조건이 된다. 이걸 빠뜨려서
리눅스에서는 통과하고 윈도우에서만 4건이 실패했다.

### 변형 주입에서 두 번 새던 것

perf 성격의 검사를 **시간으로 재려다 두 번 실패했다.**

1. `elapsed < 1.0` — rglob 판도 리눅스에서는 56ms 라 통과했다.
   출력은 어차피 같으니 시간이 유일한 차이인데, 기계가 빠르면 안 잡힌다.
2. `Path.iterdir` 감시 — rglob 은 `iterdir` 이 아니라 **`os.scandir`** 을 쓴다.
   그래서 여전히 안 잡혔다.

`os.listdir` 과 `os.scandir` 을 함께 감시해 **어디를 들여다봤는지**를 직접
세도록 고쳤다. 시간이 아니라 성질 그 자체를 본다.

| 되돌린 변형 | 잡히나 |
|---|---|
| `_show` 대신 `relative_to` 직접 | 잡힘 |
| rglob 으로 되돌리기 | 두 번 놓침 → os 수준 감시로 잡힘 |
| `SKIP_DIRS` 비우기 | 잡힘 |

## 21차 — 저장공간 자동 정리

"드라이브 용량이 제한적이어서 무한정 용량을 잡아먹으면 안 돼."

### 무엇이 쌓이나

`runs/<실행>/champion_model.joblib` 이 거의 전부다. RandomForest·앙상블이면
**한 번에 수백 MB**. 나머지(csv·json·html)는 합쳐도 수 MB다. 실행 15번이면
2.5GB 가 된다.

### 지우는 대상을 두 부류로 완전히 갈랐다

| | 무엇 | 어떻게 |
|---|---|---|
| **찌꺼기** | `__pycache__` · 점검 임시파일 · 중간에 죽어 껍데기만 남은 실행 폴더 | 조건 없이 지움 |
| **실행 결과** | 사용자 산출물 | 정책을 보여주고, 무엇이 지워질지 먼저 보여준 뒤에 |

두 번째가 핵심이다. **말없이 지우면 그건 데이터 손실이다.** 그래서
보관(KEEP) 지정한 실행은 **어떤 기준에도 안 걸리고**, 지금 화면이 쓰는 실행도
빠지며, 무엇을 왜 지웠는지 항상 보고한다.

기준은 셋이고 화면(설정 > 저장공간)에서 바꾼다 — 최신 N개(기본 10) ·
총 용량 상한(기본 2,000MB) · 보관 일수(기본 무제한). 화면을 띄울 때마다
`scripts/launch.py` 가 이 기준으로 조용히 정리하고, 뭔가 지웠을 때만 한 줄 찍는다.

### 테스트를 쓰다가 잡은 위험한 버그

**기준을 전부 0(제한 없음)으로 두면 실행 전체가 삭제 대상이 됐다.**

처음에는 "남길 것을 고르고 나머지를 지우는" 방식으로 짰다. 그러니 제한이
하나도 없으면 아무것도 '남길 것' 에 안 들어가서, **"제한 없음" 이 "전부 삭제"
로 동작했다.** 지우는 코드에서 기본값이 파괴적인 쪽이면 안 된다.
"전부 남긴다" 에서 출발해 기준에 걸리는 것만 빼는 방식으로 뒤집었다.

### 지우는 코드라 특히 조심한 것

다른 결함은 다시 돌리면 되지만 이건 사용자의 결과물이 사라진다. 그래서
테스트가 "잘 지우는가" 보다 **"지우면 안 되는 것을 안 지키는가"** 에 무게를 둔다.

- `runs/` 밖은 한 발도 안 나간다 — `..` · 홈 디렉터리 · runs 자기 자신 전부 거부
- 경로 검사를 **지우기 직전에 다시** 한다 (목록을 만들 때만 보면 그 사이 변화를 못 막는다)
- 계획을 세운 **뒤에** 보관을 지정해도 그 뜻을 따른다

| 되돌린 변형 | 잡은 테스트 |
|---|---|
| runs 경계 검사 제거 | 2건 |
| 삭제 직전 재검사 제거 | `apply_rechecks_the_path_right_before_deleting` |
| 보관 지정 무시 | `pinned_runs_survive_every_policy` |
| 제한 없음 → 전부 삭제 (원래 버그) | 2건 |

## 20차 — 앙상블 SHAP 이 끝나지 않던 문제

사용자 보고: "6. SHAP 해석 단계인데 20분 지나도 완료가 안 돼."

### 원인 — 두 개가 겹쳤다

**1. 앙상블은 커널 근사로 떨어진다.** `_estimator_kind` 의 `TREE_FAMILIES` 에
Blend 계열이 없어서, 챔피언이 `Ensemble_*` 이면 "트리도 선형도 아님" 으로
분류돼 `KernelExplainer` 가 붙었다. 표본 4,000 × 피처 46 이면 모델 호출이
**860만 번**이고, 그 한 번마다 base 파이프라인 5개가 전부 돈다.
20분이 아니라 몇 시간짜리다.

**2. 화면이 거짓말을 했다.** 더 나쁜 쪽이다.

```python
fast = any(k in champ for k in (..., "Tree", "Ensemble"))   # 화면의 짐작
```

화면은 이름에 "Ensemble" 이 있으면 **빠른 경로**라고 보고 "수 초~1분" 이라고
안내했다. core 는 정반대로 판단하고 있었다. **비용이 100배 다른 두 경로를
이름으로 짐작하면 반드시 어긋난다.** 사용자는 1분짜리인 줄 알고 20분을 기다렸다.

### 고친 방법 — 근사가 아니라 정확한 분해

이 도구의 앙상블 셋은 전부 base 예측의 **선형결합**이다.

| | 가중치 |
|---|---|
| `MeanBlend` | 1/k |
| `WeightedBlend` | nnls 가 구한 가중치 |
| `OofStack` | 메타가 선형이면 그 계수 (+절편) |

SHAP 은 가법적이므로 **예측이 선형결합이면 SHAP 도 같은 가중치의 선형결합**이다.
base 를 각각 트리 경로로 빠르게 풀어 합치면 근사가 아니라 **정확히 같은 값**이
나온다. 몇 시간 → 수십 초.

메타가 비선형이면(RandomForest 등) 이 성질이 성립하지 않으므로 **분해를
거부**한다. 억지로 합쳐 조용히 틀린 기여도를 띄우는 것이 느린 것보다 나쁘다.

### `explain.plan()` — 판단을 한 곳으로

화면은 이제 짐작하지 않고 core 에 물어본다. 어떤 설명기를 쓸지, 표본을 몇 개로
잡을지, 느린 경로인지를 `plan()` 이 정하고 화면은 그대로 옮긴다.

근사 경로에는 **표본 상한 300** 을 못으로 박았다. 사용자가 4,000을 넣어도
거기서 잘린다 — 상한 없는 근사 경로는 "끝나지 않는 계산" 이고, 그건 기능이
아니다. 함께 "순열 중요도로 대신 보기" 버튼을 그 자리에 둔다.

### 검증

수식 성질을 먼저 확인했다 — 세 블렌드 모두 `predict == Σ wᵢ·predictᵢ + b`.
그게 성립해야 SHAP 을 같은 가중치로 합치는 것이 정당하다.

| 되돌린 변형 | 잡은 테스트 |
|---|---|
| 앙상블 분해 제거 (원래 사고) | 5건 |
| 커널 표본 상한 제거 | 2건 |
| 비선형 메타도 분해 시도 | `nonlinear_meta_is_refused` |
| 가중치 0 인 멤버도 계산 | `zero_weight_members_are_not_computed` |

### `SO_REUSEADDR` — OS 마다 뜻이 반대다

|---|---|

## 17차 — run.bat 이 안 켜졌다 · 진입점 무검증 구멍

사용자 보고: "run.bat 누르니 `) 은(는) 예상되지 않습니다` 뜨고 바로 꺼짐."
그리고 정당한 질책: **"변경점 줄 때마다 회귀 테스트 필수."**

### 무엇이 잘못됐나

16차에서 `run.bat` 에 인자 처리 분기를 넣었다.

```bat
if defined A1 (
  if "%A1:~0,1%"=="-" (set "ARG=%A1%") else (set "ARG=--python %A1%")
)
```

cmd.exe 는 `( ... )` 블록을 **실행 전에 통째로 해석**하면서 안의 변수를 먼저
펼친다. 인자 없이 더블클릭하면 `%A1:~0,1%` 가 비어 문법이 무너지고
`") 은(는) 예상되지 않습니다"` 로 죽는다. 창은 그대로 닫혀서 사용자는 무슨 일이
있었는지도 못 본다.

**이 프로젝트에는 원래 원칙이 있었다** — `scripts/setup.py` 첫 줄 주석에
"배치파일은 ASCII 로만 두고, 안내와 분기는 전부 이쪽으로 옮겼다" 라고 적혀 있다.
내가 그걸 어겼다.

### 진짜 문제는 그 다음

**회귀 테스트는 288건 전부 통과한 상태로 나갔다.** 배치파일을 검증하는 테스트가
하나도 없었기 때문이다. 파이썬은 288건이 지키는데, 정작 **사용자가 제일 먼저
누르는 파일**은 아무도 안 보고 있었다.

> 커버리지가 0인 파일을 고치면서 커버리지를 먼저 만들지 않았다.
> "테스트 돌렸고 통과했다" 가 "검증했다" 와 같은 말이 아니다.

### `tests/test_entrypoints.py` (신규 12건)

`_cmd_block_parse` 가 cmd.exe 의 블록 선해석을 흉내 낸다 — **변수를 전부 빈
문자열로 펼친 뒤에도** 문법이 성립하는지 본다 (= 인자 없이 더블클릭한 상황).

| 검사 | 막는 것 |
|---|---|
| 빈 인자 더블클릭 | 이번에 터진 그것 |
| **검사기 자체 검사** | 실제로 나간 깨진 코드를 넣어 잡히는지 확인 |
| goto 라벨 존재 | 없는 라벨 → 죽고 창 닫힘 |
| ASCII 전용 | 코드페이지 사이에서 줄이 잘림 |
| 호출 스크립트 존재 | "지정된 경로를 찾을 수 없습니다" |
| pause / cmd /k | 실패해도 창이 남아야 원인을 본다 |
| `bash -n` | run.sh · report.sh 문법 |
| requirements 드리프트 | 같은 패키지가 두 파일에 |
| setup.EXTRAS ↔ requirements-extra | run.bat 로 깐 사람과 pip -r 로 깐 사람이 다른 환경이 되는 것 |

검사기 자체 검사가 핵심이다. 예전에 sprintf 검사기가 `%.2%` 를 통과시킨 적이
있다 — 조용히 아무것도 안 잡는 검사기는 없느니만 못하다.

### 고친 것

`run.bat` 에서 분기를 전부 걷어내고 `%*` 로 넘기기만 한다. `run.bat 3.12` 는

사유만 있으면 믿거나 말거나가 되고, 근거 표가 있어야 "우리 설비는 저 태그가 원래
저렇다" 는 현장 판단으로 뒤집을 수 있다.

| 항목 | 무엇을 보고 정하나 |
|---|---|
| 결측 대치 | 결측 **비율이 아니라 연속 길이**. 짧게 끊기면 ffill, 길게 비면 median |
| 스케일링 | 태그 간 변동폭 비율 · robust z 로 잰 이상값 |
| 범주 인코딩 | 값에 순서가 보이는가 (등급·레벨·A/B/C) |
| 극단값 clip | robust z 5 초과 지점의 존재 여부 |
| lag | 상호상관을 밀어 가며 **오차 감소율**이 최대인 지점 |
| rolling 창 | 타겟 자기상관이 0.5 아래로 꺼지는 지점 |
| 선별 상한 | 학습 행 수 ÷ 피처 수 (피처당 20행 경험칙) |

**물리적 한계** — 3단계 상단에 "최대 반응 지연(분) / 최대 평균 구간(분)" 을 둔다.
통계가 뭐라 하든 그 너머는 추천에서도, 선택지에서도 **사라진다** (비활성화가 아니라
제거 — 고를 수 없는 항목을 회색으로 남기면 왜 못 고르는지를 또 설명해야 한다).

### 만들면서 실제로 잡은 오추천 3건

추천 기능은 **틀린 추천이 없는 추천이 아닌 것보다 낫다** 가 성립해야 의미가 있다.
사유 문장이 그럴듯해서 사람이 검증하지 않기 때문이다. 데모 데이터로 돌려 보며 셋을 잡았다.

| 증상 | 원인 | 고친 방법 |
|---|---|---|
| 센서 하나가 60% 비었다고 멀쩡한 태그까지 median | **최악의 태그**로 전체를 판단 | 결측 있는 태그의 중앙값 기준 + 40% 초과 태그는 별도 경고 |
| 사유에 "18,091,036배 차이" | 값이 1.000001 인 태그(σ=1e-6)가 절대 임계를 통과 | 변동계수로 판정 → "77배" |
| 노이즈(상관 0.10)에서 8시간 lag 추천 + **진짜 1시간 지연은 놓침** | 절대 상관 개선치로 측정 | 상관 0.2 이상 **그리고** 오차 감소율 0.10 이상 |

세 번째가 핵심이다. 상관 0.993 → 0.999 는 절대값으로 +0.006 이라 하찮아 보이지만
**설명 못 하던 오차의 88%가 사라진 것**이다. 그래서 이렇게 잰다.

```python
left0 = max(1e-12, 1.0 - at_zero ** 2)
leftL = max(0.0, 1.0 - best_r ** 2)
gain_ratio = (left0 - leftL) / left0
```

## 14차 — 세로형(long) 데이터 지원 · 모드 안내

### 1. 세로형(long) 데이터 — 기능 추가

설비 데이터는 두 모양으로 나온다.

```
가로형(wide)                          세로형(long)
tag_time          flow  temp          tag_time          tag_name  value
2025-01-01 00:00  52.3  65.1          2025-01-01 00:00  flow      52.3
2025-01-01 00:05  52.9  65.4          2025-01-01 00:00  temp      65.1
```

**PI · IP.21 같은 히스토리언은 long 이 기본이다.** 태그를 나중에 추가해도 테이블
구조를 안 바꿔도 되기 때문이다. 그래서 사내 데이터마트에서 뽑으면 이 모양으로
나오는 경우가 아주 흔한데, 지금까지는 그걸 그대로 시계열로 만들려 했다.
**시각이 중복된 표라 태그끼리 서로 덮어써서 데이터가 조용히 망가진다.**

`core/datasource.py` 에 세 함수를 넣었다 (streamlit 을 모르는 순수 로직).

- `detect_layout()` — wide/long 판정 + 확신도 + **판단 근거 문장**
- `long_to_wide()` — 돌려 세우기. 같은 (시각, 태그) 중복은 평균·마지막값 등으로 합침
- `tag_inventory()` — 돌리기 전에 어떤 태그가 몇 줄씩 있는지 보여줌

**판정의 핵심 단서는 시각의 중복이다.** wide 는 시각마다 한 줄이라 시각이 유일하고,
long 은 태그 수만큼 같은 시각이 반복된다. 여기에 '태그 이름처럼 보이는 컬럼'
(글자 · 종류가 적당 · 여러 번 반복)과 컬럼 개수를 더해 점수를 낸다.

**오판이 더 나쁘다** — 멀쩡한 wide 를 돌리면 데이터가 망가진다. 그래서
`NORMAL/WARN/TRIP` 같은 상태 컬럼이 섞인 wide 를 long 으로 오해하지 않는지
따로 테스트한다 (시각이 안 겹치므로 wide 로 판정된다).

화면은 1단계에 '데이터 모양 확인' 을 넣었다. 두 모양을 코드 예시로 보여주고,
판단 근거를 적고, 태그 목록을 보여주고, 필요한 태그만 골라 돌릴 수 있게 했다.
**돌리기 전에는 다음 단계로 못 넘어간다** — 넘어가면 조용히 망가지므로.
자동 판단이 틀렸다고 보이면 직접 지정할 수도 있다.

`scripts/make_demo_data.py` 가 세로형 견본(`demo_timeseries_long.csv`, 116,640줄
· 태그 9개)도 함께 만든다. 1단계에 **[가상 데이터 — 세로형]** 버튼이 생겨서
바로 눌러 볼 수 있다. 견본으로 왕복을 확인했다 — 돌린 뒤 12,960행 × 9태그로
원본 wide 와 정확히 같아진다.

### 2. 모드 — 무엇이 다른지 화면에서 말한다

| 전 | 후 |

| Guided | 단계별로 (권장) |
| Expert | 전부 직접 설정 |

맨 위에 못을 하나 박았다 — **"어느 쪽을 고르셔도 검증 절차는 똑같습니다.
'Auto 라서 대충 본다' 같은 건 없습니다."** 달라지는 것은 보여주는 설정의 개수뿐이다.

### 1. 버튼 글씨가 안 보였다 (진짜 결함)

**streamlit 은 버튼 라벨을 button 안쪽 `<p>` 에 넣고 거기에 textColor 를 따로
먹인다.** CSS 는 `button` 에만 `color: #FFFFFF` 를 주고 있었으니 안쪽이 이겼고,
남색 배경에 검정 글씨가 됐다.

자손 선택자 + `!important` 로 눌렀고, streamlit 버전마다 다른 DOM

사이드바(어두운 배경)와 보조 버튼(흰 배경)은 반대 방향으로 따로 지정했다.

### 2. 말을 바꿨다 — 전체 화면

원칙 세 가지로 정리했다.

1. **라벨은 그 칸이 무슨 일을 하는지**로 쓴다. 전문용어는 도움말 끝에
   `(전문용어: 구분자)` 처럼 괄호로 남긴다 — 아는 사람은 알아보고,
   모르는 사람은 안 걸린다.
2. **왜 필요한지를 먼저 말한다.** 설정 칸 위에 접힌 설명을 두고, 공정 예시로 쓴다.
3. **자주 안 건드리는 것은 접어 둔다.** 처음 열었을 때 모르는 용어 세 개가
   먼저 보이면 파일을 올리기도 전에 막힌다.

| 전 | 후 |
|---|---|
| 구분자 | 값을 나누는 기호 — `쉼표 ,` `세미콜론 ;` 로 보여줌 |

### SQream 은 실패가 아니라 건너뜀

```
NoSuchModuleError: Can't load plugin: sqlalchemy.dialects:sqream
```

`pysqream-sqlalchemy` 를 안 깐 상태이므로 **정상 동작**이다. 그런데 점검기가
이것을 결함으로 분류했다 — SQLAlchemy 는 드라이버가 없을 때 `ImportError` 가

### 리포트 수집기가 죽으면서 파일을 안 남겼다

```
ValueError: invalid literal for int() with base 10: '누수 점검 실패'
```

`SystemExit("누수 점검 실패")` 의 `.code` 는 문자열인데 `int()` 로 바꾸려 했다.
**오류를 보여주려고 만든 도구가 오류를 감춘 셈이다.** 사용자에게는 cmd 창이
닫히고 파일도 안 생긴 것만 남았다.

세 가지로 다시 만들었다.

1. **첫 줄부터 파일에 바로 쓴다** (단계마다 flush + fsync). 중간에 죽어도
   거기까지는 남고, 파일 앞머리에 "여기까지만 있으면 그 단계에서 죽은 것"이라고
   적어 둔다.
2. **각 단계를 하위 프로세스로 돌린다.** 파이썬이 통째로 죽는 사고
   (C 확장 크래시, `os._exit`)가 나도 수집기는 살아서 기록한다.
   `os._exit(3)` 을 심어 실제로 확인했다 — 16KB 짜리 리포트가 남고 요약에
   `실패 1건` 이 찍혔다.
3. **창이 안 닫힌다** (`pause` → `cmd /k`). 콘솔 출력도 `report_console.log` 로
   따로 남는다. 파일명은 배치가 안내할 수 있도록 ASCII 로 바꿨다
   (`diagnostic_report.txt`).

### 설치가 멈춘 것처럼 보이던 것

2단계에서 출력이 멈춰 사용자가 Ctrl+C 로 끊었다. pip 이 큰 wheel 을 받거나
의존성을 맞춰 볼 때 조용해지는 구간이다.

- `--prefer-binary` — 소스 빌드를 피한다. 윈도우에서 컴파일이 걸리면 조용한 채로
  수십 분이 간다
- `--progress-bar on`, 시작 전 "한동안 안 움직여도 정상. 10분 넘기면 끊으세요" 안내
- **부스팅·SHAP 를 하나씩 설치.** 전에는 4개를 한 줄로 몰아 깔아서 catboost 하나만
  실패해도 xgboost·lightgbm·shap 까지 통째로 안 깔렸다

### 1. streamlit · plotly 대역

1. **파이썬 수준 오류** — KeyError, IndexError, AttributeError, TypeError,
   없는 컬럼 참조, None 연산. streamlit 이 있든 없든 똑같이 터지는 진짜 결함이다.
2. **진짜 streamlit 이 던지는 예외** — 위젯 기본값 범위 밖, 잘못된 `icon=`,
   잘못된 `format` 문자열, 없는 컬럼을 가리키는 `column_config`,
   옵션이 과도하게 많은 `select_slider`. 10차까지 손으로 하나씩 찾아낸 결함이
   전부 이 부류였다.

상태는 손으로 만들지 않고 **진짜 파이프라인(적재→파생→선별→분할→학습→Unseen)을
돌려서** 채운다. 손으로 만든 상태는 실제와 어긋나기 마련이고, 그러면 통과해도
의미가 없다.

**대역이 제구실을 하는지부터 확인했다.** 10차에서 고친 결함 3개(SHAP 표본 상한,
PCA 슬라이더, plotly `titlefont`)를 소스에 그대로 되심고 돌렸더니 8개 테스트가
FAIL 로 바뀌었다 — 그중 `test_every_view_renders_with_a_full_pipeline` 은
문자열 검색이 아니라 **화면을 실제로 그리다가** 잡은 것이다.

### 3. 검사기 자체의 구멍도 하나 나왔다

자기점검 테스트(`test_the_fake_catches_bad_icons_and_formats`)가 실패했다.
`"%.2%"` 를 거부해야 하는데 통과시키고 있었다.

```python
# 첫 판 — "%.2%" 가 "정밀도 .2 + 변환자 %" 로 잘못 읽혀 통과한다
re.compile(r"%[-+ #0]*[\d.]*(?:[bcdieEfgGosuxX]|%)")

# 고친 것 — 리터럴 퍼센트는 **정확히 %%** 여야 한다
re.compile(r"%%|%[-+ #0']*\d*(?:\.\d+)?[bcdieEfgGosuxX]")
```

10차에 넣은 `test_number_column_formats_are_valid_sprintf` 도 같은 정규식을 썼으므로
**그 테스트는 통과하고 있었지만 아무것도 검사하지 않고 있었다.** 둘 다 고쳤다.
검사기를 검사하는 테스트가 없었으면 영영 몰랐을 부류다.

### 2. 속도 — 측정된 낭비

**폴드 내부 선별이 쓰지도 않을 상호정보량을 계산하고 있었다.**

`TrainConfig.selection_top_k` 의 기본값은 `None` 이다. `top_k` 가 없으면 MI 는 컷오프에
쓰이지 않고 사유 문자열에만 남는데, `FoldSelector` 는 그 사유 표를 버린다. 즉 계산 결과가
어디에도 쓰이지 않는다.

이 컨테이너에서 잰 값:

| 데이터 | MI 계산 | 생략 | 축소 |
|---|---|---|---|
| 20,000행 × 120열 | 14.92s | 0.49s | 3.3% |
| 50,000행 × 200열 | 61.46s | 0.60s | 1.0% |

`fit` 한 번당이다. 폴드 5개 × 모델 12종이면 **61분이 36초**가 된다. 50만 행이면 더 벌어진다.
`select_core(compute_mi=)` 를 추가하고 `FoldSelector` 만 `bool(top_k)` 로 넘긴다 —
화면에 MI 를 보여주는 `select_features` 경로는 그대로다. 선별 결과가 달라지지 않는다는
것을 테스트로 고정했다 (`test_compute_mi_false_leaves_selection_unchanged`).

**나머지 네 가지**

- `prep_view` 의 상관행렬을 세션에 캐시. 결측이 섞인 `DataFrame.corr()` 는 쌍마다 도는
  느린 경로로 빠지는데, 슬라이더를 만질 때마다 다시 돌고 있었다. 50,000행 넘으면
  등간격 표본을 쓰고 그 사실을 화면에 적는다 (중복 후보 제안용 수치이므로).
- `download_button` 에 넘기던 `to_csv()` 를 `theme.csv_download()` 로. 버튼은 눌리기 전에도
  데이터를 갖고 있어야 해서, 접힌 expander 안에서도 재실행마다 전량 인코딩되고 있었다.
- `leakage_checklist` 가 `index.duplicated()` 를 두 번 불렀다 (`.any()` 와 `.sum()`).
  50만 행 해싱을 두 번 하던 것을 한 번으로.
- `config_view` 가 임계 슬라이더를 옮길 때마다 지난 run 폴더를 통째로 다시 읽었다.

### 3. 직관성

- **전체 초기화에 확인 단계.** 한 번 누르면 데이터부터 챔피언까지 전부 사라지는데
  경고가 없었다.
- **`invalidate()` 가 무엇을 지웠는지 알린다.** 앞 단계를 건드리면 챔피언이 조용히
  사라져서, 사용자는 자기가 뭘 잘못 눌렀는지 알 수 없었다.
- **예측이 해석 단계를 막지 않는다.** SHAP 은 챔피언만 있으면 계산된다. 필요 없는
  단계를 강제로 거치게 하던 blocker 를 권유 문구(`_advice`)로 내렸다.
- **선택 편향 크기에 읽는 법을 붙였다.** 숫자만 있고 "그래서 이게 크면 어쩌라는 건지"가
  없었다.
- **OOF 를 풀어서 설명한다.** 앙상블 화면이 "OOF 를 시계열 분할로 만든다"로 시작했는데,
  OOF 가 뭔지 모르면 읽을 수 없는 문장이었다.
- **SHAP 예상 소요를 미리 말한다.** 트리 계열인지에 따라 수 초 ~ 수 분이다. 모르면
  멈춘 줄 알고 새로고침한다.
- **Final Unseen 이 예측 구간에 들어가면 경고.** 그리는 것 자체는 접근 횟수에 안 잡히지만,
  그 그림을 보고 모델을 바꾸면 미접촉이 깨진다.
- **비지도학습이 확정 전 피처를 쓰면 경고.** 3단계에서 고른 목록으로 도는 줄 오해하기 쉽다.
- **누수 가드 배지에 툴팁**, MI·lookback·결측률 컬럼에 설명, cp949 인코딩 안내와
  `UnicodeDecodeError` 전용 메시지, "분할 다시 정하기" → "3단계로 돌아가 다시 나누기".

### 4. Final Unseen 접근권이 학습할 때마다 되살아났다 (이번 회차 최대 결함)

점검 중에 나온 것이고, 앞의 것들과 성격이 다르다. **터지지 않는다. 화면도 정상으로
보인다. 다만 보고되는 최종 성능이 낙관 편향된다.**

`UnseenGuard` 는 Final Unseen 구간을 한 번만 열도록 코드로 세는 장치다. 그런데
가드를 만드는 자리가 **학습 실행** 안이었다 (`train_view.py:185`). 그리고
`invalidate("train")` 이 `unseen_guard` 를 지웠다. 그래서 이런 순서가 가능했다.

1. 학습 → 챔피언 A → 가드 생성 (접근 0회)
2. Final Unseen 평가 → 접근 1회, 점수 확인
3. 점수가 마음에 안 듦 → **[학습 실행] 을 다시 누름** (분할·피처는 그대로)
4. `invalidate("train")` 이 가드를 지우고, 새 가드가 접근 0회로 생성
5. Final Unseen 평가 → **또 통과**

가드가 띄우는 문구는 "모델을 바꾸려면 분할부터 다시 하세요" 인데, 화면은 분할을
다시 하지 않고도 그 상태로 되돌려 주고 있었다. 만족스러운 숫자가 나올 때까지
반복하면 Final Unseen 은 사실상 두 번째 검증 구간이 되고, 3분할을 도입한 이유가
사라진다.

거기에 뒷문이 하나 더 있었다. `evaluate_unseen(guard=None)` 이 **횟수 제한 없이
통과**했다. 리더보드에서 챔피언을 바꾸면 `S.unseen_guard` 가 None 이 되는 경로가
있어서, 그 상태에서는 몇 번이든 열렸다.

**고친 방식** — 접근권은 학습이 아니라 **분할에 딸린 것**으로 옮겼다.

| | 전 | 후 |
|---|---|---|
| 만드는 곳 | 학습 실행 (`train_view`) | 분할 확정 (`features_view`, 3단계) |
| `invalidate("train")` | 지움 → 재생성 | 건드리지 않음 |
| `invalidate("features"/"split")` | 지움 | 지움 (분할이 바뀌었으므로 정당) |
| `guard=None` | 무제한 통과 | `UnseenAccessError` |

이미 쓴 접근권으로 화면에 들어오면 버튼을 눌러 예외로 알게 하는 대신, 누가 언제
열었는지와 "3단계로 돌아가 분할부터 다시 하라"를 먼저 적는다.

회귀 테스트 4건을 붙이고 **결함을 다시 심어 실제로 잡히는지 확인했다** —
`test_evaluate_unseen_refuses_to_run_without_a_guard` 와
`test_unseen_guard_belongs_to_the_split_not_the_training_run` 이 둘 다 FAIL 로 바뀌었다.

### 5. 완료된 실행을 가리키는 상태가 정리되지 않았다

`DEFAULTS` 57개 중 어느 `invalidate` 체인에서도 안 지워지는 키가 23개였다. 대부분은
정당하다 (입력 데이터, 설정값, UI 선택). 하지만 다섯 개는 **완료된 실행 하나를
가리키는 손잡이**였다 — `run_dir`, `saved`, `manifest`, `report_html`, `challenger`.

앞 단계를 건드리면 리더보드·챔피언은 지워지는데 이것들은 남았다. 결과:

- 리포트 화면이 예전 실행의 저장 경로를 "지금 저장 위치"로 표시
- Champion–Challenger 가 **예전 manifest 의 데이터 지문을 '지금 지문'으로 삼아**
  지난 run 과 비교 (`config_view.py:183`). 데이터가 바뀌었는데 "지문이 같다"고
  하거나 그 반대가 된다

디스크의 run 폴더는 기록이므로 그대로 두고, 세션이 "지금 것"이라고 붙들고 있는
손잡이만 놓게 했다. `invalidate("train")` 에도 넣었다 — 챔피언이 바뀌면 리포트도
그 챔피언 얘기가 아니다.

같은 이유로 Auto 모드의 `_apply` 가 상태를 꽂기 전에 `invalidate("data")` 를 먼저
부른다. 수동으로 한 번 돌려 리포트까지 저장한 뒤 Auto 를 돌리면 예전 예측·리포트가
새 실행의 것처럼 남아 있었다.

### 6. 테스트 러너의 skip 이 가짜였다

내장 대역의 `pytest.skip` 이 `lambda: None` 이었다. 진짜 pytest 는 예외를 던져 그 자리에서
끝내는데, 대역은 그냥 돌아와서 **skip 뒤의 코드가 그대로 실행됐다.** 없는 라이브러리를
건드리는 테스트가 조용히 통과하거나 엉뚱한 곳에서 죽는다. 7차에서 겪은 fixture 문제와
같은 부류다 — 대역과 실물의 동작이 갈리는 지점.

`Skipped` 예외를 만들고 `importorskip` 을 추가했다. 건너뛴 항목은 실행 결과 맨 아래에

### 7. 한글 윈도우에서 em dash 하나로 실행이 죽는다

점검을 마저 하다 나왔다. **cp949 에는 em dash(`—`, U+2014)가 없다.**

```
UnicodeEncodeError: 'cp949' codec can't encode character '—'
```

이 프로젝트는 출력에서 `—` 를 아주 많이 쓴다 (스크립트 15개 전부). 그런데
지금까지 안 터진 이유가 있다 — 콘솔 창에 **바로** 찍을 때는 파이썬이 UTF-16

파이프로 넘기는 순간이다. 그때는 `locale.getpreferredencoding()` = cp949 로
떨어진다.

즉 **결과를 로그로 남기려다 실행 자체가 실패한다.**

```

python tests\run_tests.py | more
```

비교했다.

## 9차 — icon 인자 오류 · SQream 지원

### 1. 파생변수 화면 하단에 크게 뜨던 오류

```
StreamlitAPIException: The value "◧" is not a valid emoji.
Shortcodes are not allowed, please use a single character instead.
```

`st.info(..., icon="◧")` 이 원인이다. Streamlit 의 `icon=` 은 **실제 이모지만**
받는데 "◧"(U+25E7)는 기하도형 문자다. 이 프로젝트는 웹폰트·이모지를 쓰지 않기로
했으므로 파라미터 자체를 뺐다 — `st.warning`/`st.info` 는 기본 아이콘이 있어서
표시에 문제가 없다. 17곳.

화면이 뜨긴 떴기 때문에 렌더링 테스트 없이는 못 잡는 종류였다. 소스에서
`icon=` 사용을 직접 막는 회귀 테스트를 넣었다.

### 2. SQream 지원

| | 값 |
|---|---|
| SQLAlchemy 방언 | `sqream` |
| 접속 URL | `sqream://user:password@host:3108/database` |
| 기본 포트 | 3108 |
| 설치 | `pip install pysqream-sqlalchemy` |
| 클러스터 접속 | `connect_args={"clustered": true}` |

DBMS 목록 맨 위에 두었다. 그러면서 세 가지가 같이 좋아졌다.

- **기본 포트 자동 입력** — 방언을 고르면 포트 칸이 채워진다 (`DEFAULT_PORTS`)
- **드라이버 패키지 안내** — "이 DBMS 는 `pip install pysqream-sqlalchemy` 가 필요합니다"
- **connect_args 입력란** — URL 이 아니라 드라이버에 직접 넘겨야 하는 옵션.
  SQream 의 `clustered` 가 그렇다. 방언별 기본값을 미리 채워 준다 (`DEFAULT_CONNECT_ARGS`)

`SqlAlchemySource` 는 원래 `connect_args` 를 받고 있었는데 화면에서 넘겨주지
않고 있었다. 접속 확인과 실행 양쪽에 배선했다.

비밀번호는 URL 인코딩되고(`p@ss w0rd` → `p%40ss+w0rd`), 화면 표시와 `runs/`
기록에서는 마스킹된다.

**미검증** — SQLAlchemy 를 설치할 수 없어 실제 SQream 접속은 못 돌려봤다.
URL 조립·마스킹·connect_args 전달까지는 테스트로 확인했다.

**(a) 옵션 12,948개짜리 슬라이더**

```python
valid_cut = st.select_slider("검증 시작 시각", options=list(idx), ...)
```

날짜 경계를 고르라고 넣은 위젯인데, `options` 에 전체 인덱스를 넘겼다. 12,948행이면

검토 게이트가 선택이 바뀔 때마다 `st.rerun()` 을 불렀다. 위젯 조작은 그 자체로

클릭이 씹히는 느낌의 정체다.

`st.rerun()` 을 걷어내고 `data_editor` 반환값을 그대로 상태에 반영한다. 다만 일괄
선택 버튼은 편집표를 새로 그려야 반영되므로(에디터가 자기 편집 상태를 `key` 로
붙들고 있다) `review_gen` 세대 번호를 키에 넣어 그때만 remount 한다.

**(c) 위험 점검이 매 재실행마다 상관행렬을 만듦**

8,000행 × 40열 상관행렬을 체크박스마다 다시 구하고 있었다. 선택 집합을 키로

**(d) 12,948점을 SVG 로 그림**

점 하나가 DOM 노드 하나다. 한 화면에 차트가 서너 개면 스크롤조차 버벅인다.

| | 이전 | 이후 |
|---|---|---|
| actual_vs_pred | 12,948점 × 2 | **3,237점 × 2** (25%) |
| residual_band | 12,948행 × 4 트레이스 | **3,237행 × 4** |

**원본은 건드리지 않는다.** 줄이는 것은 그리기 직전의 사본뿐이고, 통계·모델 계산은

기본을 "빠르게 훑기"(가벼운 모델 3종 · 폴드 3개)로 바꿨다. 화면이 도는지 먼저

### 1. 테스트 러너가 정작 pytest 가 깔린 환경에서 깨졌다 ★

사용자 PC 에서 **62 통과 / 77 실패**. 이 컨테이너에서는 146 전건 통과.

원인은 `run_tests.py` 의 fixture 탐지다.

```python
def _ensure_pytest():
    try:
        import pytest      # 있으면 진짜 pytest 를 쓴다
        return True
    except ModuleNotFoundError:
        _install_stub()    # 없으면 내장 대역
        return False

def _fixtures(mod):
    # 그런데 이 표식은 내장 대역만 붙인다
    return {n: f for n, f in vars(mod).items() if getattr(f, "__is_fixture__", False)}
```

진짜 pytest 의 `@pytest.fixture` 는 `__is_fixture__` 를 붙이지 않는다. 8.4 미만은
`_pytestfixturefunction` 을, 8.4 이상은 원본 함수를 감싼 객체를 돌려준다. 그래서
pytest 가 설치돼 있으면 `_fixtures()` 가 **빈 사전**을 반환하고, fixture 를 받는
테스트 전부가 인자 없이 호출돼 `TypeError` 로 죽었다.

이 컨테이너는 pypi 차단으로 pytest 를 끝내 설치하지 못했다. 그래서 **검증된 적
없는 분기가 실제 사용 환경의 기본 경로**였다. 테스트 도구 자체가 환경에 따라
다르게 도는 것이 문제의 본질이라, 기본 경로를 하나로 고정했다.

- 기본은 **항상 내장 대역**. pytest 설치 여부와 무관하게 같은 경로로 돈다
- `--pytest` 를 주면 진짜 pytest 에 위임한다
- `_fixtures()` 는 표식 세 가지를 모두 알아본다 (내장 / pytest<8.4 / pytest>=8.4)

pytest 가 설치된 환경을 흉내내 재현하고, 두 경로 모두 146 통과를 확인했다.

### 2. run.bat 이 리눅스 줄바꿈(LF)이었다

윈도우 배치파일은 CRLF 여야 한다. cmd 가 명령을 잘못 읽어 줄마다 에러가 났다.

### 3. `chcp 65001` + 한글 = cmd 파싱 붕괴

코드페이지를 바꾸면 cmd 가 배치파일의 **바이트 위치를 잃는다.** 주석 줄 중간이
잘려 `'하다.' is not recognized` 같은 조각이 명령으로 실행됐다.

배치파일을 **순수 ASCII** 로 두고 실제 작업은 `scripts/setup.py` 로 옮겼다.
파이썬은 UTF-8 을 제대로 다루므로 한글 안내가 정상으로 나오고, 윈도우·맥·리눅스가
같은 코드를 쓴다. 파이썬 버전이 검증 범위(3.10~3.12)를 넘으면 미리 경고하고,
핵심 패키지 설치가 실패하면 원인별 대처를 안내한다.

### 덧 — 의존성 분리

`requirements-core.txt`(필수) / `requirements-extra.txt`(부스팅·SHAP)로 나눴다.
pip 은 하나만 실패해도 전체를 롤백하므로, CatBoost 하나 때문에 streamlit 조차
안 깔리는 사고를 막는다.

## 6차 — 해석 화면 라벨 · 리포트 보강 · Auto 모드

### 1. 해석 화면이 검증 구간을 'unseen' 이라 부르던 문제

3분할을 넣은 뒤에도 화면 라벨이 2분할 시절 그대로였다. `explain_view` 가
`"홀드아웃 (unseen)": X.iloc[S.test_idx]` 로 표시하는데, 3분할에서 `test_idx` 는
**검증 구간**이다. 모델을 고르는 데 이미 쓴 구간을 미접촉 구간이라고 부르면
그 점수를 최종 성능으로 보고하는 사고로 이어진다.

| 화면 | 이전 | 이후 |
|---|---|---|
| SHAP 계산 대상 | 학습 / 홀드아웃(unseen) / 전체 | 학습 / **검증(모델 선택에 사용됨)** / **Final Unseen(최종 보고 구간)** / 전체 |
| 예측 성능 | 학습 구간 / 홀드아웃(unseen) | 학습 / 검증 / Final Unseen — 구간마다 무엇을 뜻하는지 한 줄 설명 |
| 예측 구간 선택 | "홀드아웃만" 체크박스 | 학습 / 검증 / Final Unseen 빠른 지정 |
| 리더보드 | "holdout_ 은 학습에 안 쓴 마지막 구간" | 3분할이면 "검증 구간이며 챔피언 선정에 쓰임" |
| 과적합 점검 | 학습 대비 **홀드아웃** | 학습 대비 **검증** |

SHAP 대상으로 Final Unseen 을 고르면 경고를 띄운다 — SHAP 계산 자체는 성능 평가가
아니라 접근 횟수에 포함되지 않지만, 거기서 본 결과로 모델을 바꾸면 그 구간은 더 이상
미접촉이 아니다.

### 2. HTML 리포트 보강

리포트에 절반만 담기고 있었다. 항목을 16개로 늘렸다.

신규: **Final Unseen**(맨 앞 — 이것이 보고값), 구간 분할, 앙상블 자동채택 판정,
폴드 안정성, 잔차 진단(drift·이상점·자기상관), Rolling Backtest, Random vs Time 진단,
피처 선별 이력(수동 변경 포함), 재현 기록(지문·seed·패키지·구간 경계).

상단 요약의 우선순위도 바꿨다. Final Unseen 점수를 먼저 놓고 검증 점수를 뒤에 둔다 —
같은 자리에 나란히 놓으면 어느 쪽이 보고값인지 흐려진다.

### 3. Auto 모드 원클릭 실행 — `core/pipeline.py` (신규)

모드가 노출 범위만 줄이고 자동 실행은 하지 않아 이름값을 못 하고 있었다.
`run_auto(df, target)` 하나로 품질 진단 → 파생 → 분할 → 선별 → 누수 점검 → 학습 →
앙상블 → Final Unseen 까지 돈다. `core` 에 뒀으므로 Dataiku Scenario 에서도 그대로 쓴다.

**자동화되는 것은 '사람이 버튼을 누르는 일' 이지 '검증을 생략하는 일' 이 아니다.**
3분할·gap 자동 설정·선별 구간 추적·폴드 내부 선별·Unseen 1회 접근이 전부 그대로 돌고,
누수 점검을 통과하지 못하면 `AutoRunError` 로 **학습 전에 멈춘다**.

사람이 고르던 값은 기본값으로 대체하되 무엇을 어떻게 정했는지 표로 남긴다.

```
단계          항목            결정                            근거
품질     제외 컬럼            1개                 결측·상수·편중·중복 규칙에 걸린 컬럼
파생  최대 lookback           24행                      gap 을 이 값으로 맞춥니다
분할            구간   학습 8,361 / 검증 2,587 / Unseen 1,940
                              Final Unseen 을 확보해 모델 선택과 최종 보고를 분리
선별       선택 피처   25개 / 109개 후보         분산 → 상관중복(0.98) → MI 상위 25
보고       최종 성능   Final Unseen R2 0.9774   학습·선별·모델선택 어디에도 안 쓰인 구간
```

### ★ Auto 결정 표를 보다가 찾은 버그 — 챔피언이 잘못 뽑히고 있었다

리더보드 1위와 챔피언이 달랐다. 원인은 **family 이름 충돌**이다.

```python
# models.py — sklearn 분류상 배깅 모델의 family 는 "ensemble" 이다
put(ModelSpec("RandomForest", ..., "ensemble", True))
put(ModelSpec("ExtraTrees",   ..., "ensemble", True))

# ensemble.py — 그런데 여기서는 "우리가 만든 결합 모델" 을 뜻했다
singles = ok[ok.get("family", "") != "ensemble"]   # RF·ET 가 여기서 빠진다
```

그래서 `adopt_ensemble` 이 RandomForest·ExtraTrees 를 "3% 임계를 넘어야 하는 앙상블
후보" 로 분류했다. demo 데이터에서 **실제 1위인 ExtraTrees(0.9654)가 챔피언에서 밀려나고**
HistGradientBoosting(0.9637)이 뽑혔다.

결합 모델의 family 를 `"blend"` 로 바꾸고, 예전에 저장된 리더보드를 위해 `Ensemble_`
이름 접두사도 함께 본다. 회귀 테스트 2건을 붙였다.

이 버그는 조용히 틀린 모델을 고르고 있었고, **Auto 모드가 결정 근거를 표로 뱉지
않았다면 못 찾았다.** 판단 근거를 남기는 것이 그 자체로 검증 장치가 된다.

### 그 외

- `run_tests.py` 대역에 `monkeypatch` 와 `pytest.raises(match=)` 추가.
  누수 점검 실패 경로를 pytest 없이도 테스트할 수 있어야 한다.
- `report.py` 하단 문구가 2분할 기준이던 것을 3분할 설명으로 교체.

### 테스트

## 5차 — 3단계 검토 게이트 (사용자 요청)

파생변수까지 만든 뒤, **학습으로 넘어가기 전에 사람이 X 피처를 확정하는 관문**을 넣었다.
자동 선별은 추천으로 남기고 최종 판단은 사람이 한다. 도메인 판단이 통계보다 옳은
경우가 많기 때문이다.

### 흐름 변경

```
이전  3단계 [선별 실행] → 자동 선별 결과가 곧 X → 4단계 학습
이후  3단계 [품질 리포트 만들기] → 검토 화면 → [이 목록으로 확정] → 4단계 학습
```

확정 전에는 `S.X` 가 만들어지지 않으므로 학습 화면이 막힌다. 리포트만 만들고 넘어가면
"아직 확정 전입니다" 안내가 뜬다.

### 여기서 가장 조심한 것 — 사람이 누수 경로가 되는 문제

알고리즘이 홀드아웃을 못 보게 막아 놓고, 사람에게는 전체 구간 통계를 보여주면
**사람이 그 통계를 보고 피처를 고르는 순간 누수**다. 그래서 검토 화면의 숫자
(MI · 분산 · 결측률 · 학습구간 평균/표준편차 · 상관)를 **전부 학습 구간에서만** 계산한다.

회귀 테스트로 못박았다 — 검증·Unseen 구간을 1e4 배로 오염시켜도 검토 표의 모든
수치가 바뀌지 않아야 한다 (`test_review_report_ignores_validation_and_unseen`).

### 화면 구성

| 요소 | 내용 |
|---|---|
| 원본 컬럼별 요약 | `flow 10개 중 7개 선택` 식 롤업. 파생이 많을 때 이 단위로 보는 게 빠르다 |
| 편집표 | 체크박스로 직접 켜고 끔. MI·MI순위·원본·변환·lookback·결측률·자동 판정 사유 |
| 필터 | 원본 컬럼별 / 변환 종류별 / 이름 검색 / "자동 추천에서 탈락한 것만" |
| 일괄 선택 | 자동 추천대로 · 전체 · 해제 · 원본 컬럼만 · MI 상위 30 |
| 위험 경고 | 상관 중복 동시선택, 분산 0, 결측 과다, 정보량 0 |
| 확정 | 자동 추천 대비 추가/제외 건수를 먼저 보여주고 확정 |

필터를 걸어도 **가려진 선택은 유지된다.** 필터가 선택을 지우면 대량 피처에서 사고가 난다.

### 위험 경고는 막지 않는다

경고만 하고 선택은 그대로 반영한다. 도메인 지식이 통계를 이기는 경우가 흔하고,
"이 태그는 물리적으로 반드시 들어가야 한다"는 판단을 도구가 뒤집으면 안 된다.
다만 무엇을 감수하는지는 알려 준다.

### 감사 이력 — 사람이 바꾼 것도 답할 수 있어야 한다

`apply_manual_selection()` 이 자동 판정과 달라진 부분에 표식을 남긴다.

```
feature   status              reason
flow      removed(수동제외)    사용자가 직접 제외 (자동 판정: MI 상위 1위)
valve     selected(수동추가)   사용자가 직접 추가 (자동 판정: MI 순위 46위 (상위 25 밖))
```

`manifest.json` 에 `manual_overrides` 로 함께 저장된다. `build_manifest` 의 status
필터를 접두사 비교로 바꿔서 수동 변경분이 기록에서 빠지지 않게 했다.

### 신규 함수 (`core/features.py`)

| 함수 | 역할 |

| `feature_report(report, provenance, X_train)` | 선별 결과 + 출처 대장 + 학습구간 통계를 한 표로 |
| `origin_rollup(report)` | 원본 컬럼별 생성/선택 집계 |
| `apply_manual_selection(report, chosen)` | 사람의 선택 반영 + 오버라이드 이력 기록 |
| `selection_risks(chosen, report, X_train)` | 위험 조합 탐지 (막지 않음) |

### 6. Residual 분석 확장 — `core/diagnostics.py` (신규)

R2 한 숫자로는 "어디서 어떻게 틀렸는지"가 안 보인다. 잔차를 시간축에 놓고 본다.

|---|---|
| `rolling_stats` | 잔차의 국소 평균·표준편차. 특정 구간에서만 생기는 편향 |
| `drift_table` / `drift_verdict` | 구간별 MAE·std 이동. 첫 구간 대비 배율로 모델 노후를 판정 |
| `outliers` | robust z(중앙값·MAD) 기준 이상점. 평균을 쓰면 이상점이 스스로를 정상으로 만든다 |
| `autocorrelation` | 잔차 자기상관. 남아 있으면 아직 못 뽑아낸 시간 구조가 있다 |
| `summary` | 편향 방향·크기 한 줄 요약 |

SPEC §20(잔차 기반 이상감지)을 나중에 붙이려면 잔차 계산이 화면에서 분리돼 있어야 해서
`plots` 나 view 가 아니라 core 모듈로 뒀다. 차트 3종(`residual_band` `residual_drift`
`residual_acf`)을 `plots.py` 에 추가하고 예측 화면에 붙였다.

### 9. Lag 물리시간 지정

`FeatureConfig` 에 `lag_minutes` / `rolling_minutes` 추가. `step_minutes()` 가
샘플링 간격을 읽어 `minutes_to_rows()` 로 환산한다. 5분 간격에서 60분 → 12행.

**주의해서 다룬 지점**: 이 환산값이 곧 `warmup_rows`(= gap 점검의 `max_lookback`)가
된다. 분 지정을 빠뜨리면 P0-4 에서 고친 gap 점검이 다시 무력해진다. 그래서

- `warmup_rows(cfg, index)` 로 index 를 받으면 환산까지 반영하도록 바꾸고
- 호출부 4곳(features_view · train_view · report_view · smoke_test)에 index 를 전달했다
- 간격을 모르면 **환산하지 않는다**. 어림짐작으로 행 수를 만들면 lookback 이 실제와 어긋난다

`resolve_config` 는 합집합이라 두 번 불러도 결과가 같다(멱등). `generate` 안에서도
한 번 더 부르므로 core 를 직접 쓰는 경로에서도 안전하다.

### 10. 재현성 필드 보강 — `persist.py`

`manifest.json` 신설. SPEC §26 요구 14항목을 채운다.

```json
{"run_id": "...", "dataset": {"sha256": "...", "rows": 12948},
 "seed": 42, "champion": "HistGradientBoosting",
 "split_bounds": {"train": {...}, "valid": {...}, "unseen": {...}},
 "packages": {"numpy": "...", "scikit-learn": "...", "python": "..."},
 "features_excluded": [{"feature": "...", "reason": "..."}],

```

지문은 전체 해싱 대신 형태·컬럼·dtype + 균등 표본 행의 해시를 합쳐 만든다.
큰 데이터에서 느려지지 않으면서 값이 하나만 바뀌어도 달라진다.

`compare_manifests(a, b)` 로 두 run 을 대조한다. "지난달 결과가 안 나온다"의 원인은
대개 데이터 지문 아니면 패키지 버전이다.

### 11. Rolling Backtest

`validation.rolling_windows()` + `train.rolling_backtest()`.
CV 와 목적이 다르다 — CV 는 모델을 고르려고 점수를 **평균**내고, backtest 는 시기마다
성능이 어떻게 달라지는지 보려고 점수를 **나열**한다. 한 번의 홀드아웃 점수가 운이었는지
실력이었는지 가른다. expanding(누적) / sliding(고정창) 둘 다 지원.

`backtest_summary()` 가 구간 간 표준편차와 최악 구간을 짚는다.

### 7. Random vs Time 진단 — **진단 전용** (G-3 결정)

`validation.random_split()` 과 `train.random_vs_time()`.
같은 모델을 두 방식으로 평가해 격차를 본다. 격차가 크면 데이터에 시간 구조가 강하다는
뜻이고, 그 경우 Time 쪽 숫자만 믿어야 한다.

`diagnostics.split_gap_causes()` 가 원인 후보를 제시한다.

| 원인 후보 | 근거 |
|---|---|
| 자기상관 | 타겟 lag1 자기상관이 임계 이상 |
| 분포 drift | 타겟 평균이 앞뒤 구간 사이 N σ 이동 |
| 입력 drift | 어떤 X 피처 평균이 크게 이동 — 센서 교정·운전조건 변경 의심 |
| lag mismatch | 격차는 큰데 위 둘로 설명이 안 됨 |

**격리 장치**: 결과 dict 에 `purpose: "diagnostic"` 표식을 넣고
`train.assert_not_diagnostic()` 이 평가 경로 유입을 예외로 막는다. G-3 은
"진단 목적으로만 제공하고 챔피언 선정에서는 제외" 였으므로, 사람이 지키게 두지 않았다.

### G-6. 하이퍼파라미터 탐색 — `core/tuning.py` (신규, 기본 OFF)

"P3 끝난 뒤 추가" 결정에 따라 넣었다. **nested CV** 로만 돈다.

```
바깥 폴드 k        [ 학습 ][ 검증 ]
                    │        └ 이 점수만 보고한다
                    └ 이 안에서 다시 나눠 파라미터를 고른다
안쪽 폴드 (학습 안) [ 학습 ][ 검증 ]  ← 파라미터 선택 전용
```

같은 구간에서 파라미터를 고르고 그 구간 점수를 성능이라 부르면, 홀드아웃을 모델 선택과
최종 보고에 겸용했던 것(D-3)과 **똑같은 편향**이 생긴다. 조합을 많이 볼수록 더 낙관적이 된다.

- `RandomizedSearchCV(cv=TimeSeriesSplit)` — KFold 를 쓰면 미래 구간을 보고 고르게 된다
- 그리드는 모델 12종에 대해 효과가 큰 축만 좁게 잡았다. 넓히면 비용만 늘고 과적합 위험이 커진다
- `stability()` 로 폴드마다 고른 값이 얼마나 흔들리는지 표로 낸다. 흔들리면 그 축은
  데이터가 결정해 주지 않는다는 뜻이라 튜닝 결과를 그대로 믿기 어렵다
- 기본 OFF. 켜지 않은 사람이 비용을 물면 안 된다

**누수 테스트**: 검증·Unseen 구간을 1e5 만큼 오염시켜도 선택된 파라미터가 바뀌지 않아야
한다 (`test_tuning_never_touches_validation_or_unseen`).

### 1. 스태킹 OOF 자체 구현 — `core/ensemble.py` (신규)

sklearn `StackingRegressor` 는 내부에서 `cross_val_predict` 를 부르는데, 이 함수는
모든 샘플이 정확히 한 번씩 validation 에 들어가는 분할만 받는다. `TimeSeriesSplit` 은
선두 `n/(k+1)` 구간이 어느 fold 에도 안 들어가므로 **항상** 예외가 났다.

직접 OOF 를 만드는 방식으로 교체했다. `train._fit_one` 이 이미 만들어 두고
아무도 안 쓰던 `_oof` 를 그대로 재사용한다.

| 클래스 | 역할 |
|---|---|
| `oof_matrix` | detail 의 `_oof` 를 모아 메타 학습 행렬 구성. 선두 NaN 행 제거 |
| `OofStack` | RidgeCV 메타학습기를 OOF 로 학습 |
| `WeightedBlend` | `scipy.optimize.nnls` 로 음수 없는 가중치 (SPEC §15) |
| `MeanBlend` | 단순 평균 (기존 Voting 과 동일 값) |
| `adopt_ensemble` | SPEC §17 자동채택 판정 |

**부수 효과 — base 를 재학습하지 않는다.** `train_all` 이 만든 `_pipeline` 을 그대로
쓰므로 앙상블 3종 전체가 12,948행 기준 **108초 → 4.4초** 로 줄었다.

`build_ensembles` 는 시그니처를 유지한 채 위임한다 (`detail=` 키워드 추가). 분류는
기존 sklearn Voting 경로를 그대로 둔다.

### 2. Split 단일화 + 선별구간 추적

3단계와 4단계가 각자 `time_holdout` 을 부르던 것을 **3단계 단독 결정**으로 바꿨다.

- `features_view` 가 `validation.Split` 을 만들어 state 에 넣는다
- `train_view` 는 읽기만 한다. 바꾸려면 "분할 다시 정하기" → `invalidate("split")` → 3단계 재실행
- `state.py` 에 `split` `unseen_idx` `selection_train_idx` `unseen_guard` 추가
- 무효화 체인에 `split` 단계 신설. 선별 결과와 split 은 한 몸으로 묶어 함께 비운다

**탐지 장치**: `leakage_checklist` 에 `선별 구간 격리` 항목 신설. 시간 순서가 아니라
"선별에 실제로 쓴 인덱스"와 "평가 구간 인덱스"의 교집합을 본다.

```
선별 구간 격리  실패  선별에 쓴 120행이 평가 구간에 들어갔습니다
                     (2025-01-02 19:20:00 ~ 2025-01-03 05:15:00)
```

### 3. Final Unseen 3분할 — 비율·날짜 양쪽 지원 (D4)

```
[  Train  ][gap][ Validation ][gap][ Final Unseen ]
   학습·선별        모델 선택          최종 보고 (1회만)
```

- `three_way_split(n, valid_ratio, unseen_ratio, gap)` — 비율
- `three_way_split_by_date(index, valid_cut, unseen_cut, gap)` — 날짜 (운전조건 변경 시점 경계)
- `build_split(cfg, index)` — 둘 중 하나를 고름
- `Split` dataclass — `describe()` 로 구간표, `assert_disjoint()` 로 무교집합 단정

**접근 횟수를 코드가 센다.** `UnseenGuard` 가 두 번째 접근을 `UnseenAccessError` 로 막는다.
사람이 규율로 지키게 두지 않는다.

```python
guard = train.UnseenGuard(split.unseen)
train.evaluate_unseen(pipe, X, y, split.unseen, cfg, guard)   # 1회
guard.open("두번째")                                            # UnseenAccessError
```

`selection_bias_report` 가 검증 점수와 unseen 점수의 격차를 표로 남긴다.

**하위호환 (G-5 결정: 신규만 3분할, 구버전 표기)**
`unseen_ratio=0` 이면 기존 `time_holdout` 과 **경계가 정확히 일치**한다
(`test_unseen_ratio_zero_matches_legacy_two_way` 가 3가지 조합으로 단정).
2분할 모드에서는 화면에 "홀드아웃이 선택과 보고를 겸하므로 낙관 편향" 경고를 띄운다.

### 4. `gap 확보` 점검 실제 구현

```python
# 이전 — gap >= 0 은 항상 참
add("gap 확보", gap >= 0 and (max_lookback == 0 or gap >= 0), ...)
# 이후
ok_gap = max_lookback == 0 or gap >= max_lookback
```

`gap < max_lookback` 이면 학습 마지막 행과 검증 첫 행의 입력 창이 같은 원자료를 공유한다.
실패 시 "gap 을 N행 이상으로 올리세요" 를 함께 표시한다.

### 12. 폴드 내부 Feature Selection — 기본 ON (D5)

**설계**: 선별을 Pipeline 안에 넣었다. 전처리와 같은 원칙이다.

```
Pipeline([("prep", 전처리), ("select", FoldSelector), ("est", 모델)])
```

Pipeline 안에 있으면 sklearn 이 폴드마다 `fit` 을 다시 부른다. 밖에서 한 번만 선별하면
fold-1 의 검증 구간이 이미 선별에 관측된 상태라 CV 점수가 낙관 편향된다 (D-4).

- `select_core()` 로 3단계 선별(분산→상관→MI)의 알맹이를 분리. `select_features`(DataFrame
  경로)와 `FoldSelector`(Pipeline 경로)가 **같은 함수**를 쓴다. 두 경로가 갈리면 폴드 내부
  선별을 신뢰할 수 없어서 `test_select_core_matches_select_features` 로 동일성을 단정한다.
- `TrainConfig.fold_selection` 토글 (기본 True), `selection_top_k` 로 폴드별 상한
- `jaccard_stability()` — 폴드 간 선별 중복도. 낮으면 "어떤 피처를 고르는지가 구간마다
  흔들린다"는 뜻이라 피처 해석을 조심해야 한다는 신호다.

### 측정 결과

**3분할 도입 전후 — `scripts/compare_split.py`**

시드 8개, 모델 6종, 3,000행 25피처, drift 있는 합성 시계열.

| 지표 | 값 |
|---|---|
| 낙관편차 (검증 R² − Unseen R²) 평균 | **+2.85** |
| 낙관편차 중앙값 | +1.24 |
| 낙관편차가 양수인 횟수 | **8/8** |
| 선택손실 (unseen 최고 모델 − 우리 챔피언) 평균 | **+1.93** |

낙관편차에는 두 가지가 섞여 있다. (a) N개 중 1등을 뽑은 max-of-N 효과, (b) 검증
구간과 unseen 구간 사이의 분포 drift. **선택손실** 은 (a) 만 분리한다 — 검증이 완벽한
대리지표였다면 0 이어야 하는데 평균 +1.93 이다. 검증에서 고른 챔피언이 unseen 에서는
최고가 아니었다는 뜻이고, 이것이 홀드아웃 재사용의 직접적 대가다.

**주의 — 반대 방향도 나온다.** demo 데이터(12,948행, drift 약함)에서는
검증 R² 0.9618 < unseen R² 0.9774 로 **unseen 이 더 좋았다**.

```
지표  검증(모델선택에 사용)  Final Unseen(최종 보고)      격차  비교한 모델 수
R2         0.961819              0.977437          -0.015617       9
```

즉 "3분할을 넣으면 숫자가 떨어진다"가 아니다. **떨어지는지 아닌지를 알 방법이 생긴다**가
정확한 서술이다. 세 번째 구간이 없으면 어느 경우인지 판별할 수단 자체가 없다.

**폴드 내부 선별 비용 — `scripts/bench_selection.py` (2코어 실제 측정)**

| 행 | 피처 | 선별 1회 | 4폴드 선별 | 추가시간 |
|---|---|---|---|---|
| 3,000 | 60 | 0.66s | 1.29s | +0.63s |
| 12,000 | 200 | 9.34s | 17.17s | +7.82s |
| 30,000 | 200 | 23.41s | 46.78s | +23.37s |

MI 계산만 놓고 보면 대화 세션 측정치와 거의 같다. 그런데 **Pipeline 전체를 켜고 끄면
이야기가 다르다.**

| 조건 | 전체 학습시간 | 폴드간 Jaccard |
|---|---|---|
| 선별 OFF (40피처로 시작) | 11.2s | — |
| 선별 ON (200피처 → 폴드별 40) | 62.2s | **0.265** |

**+455%.** 대화 세션이 추정한 "5~15%" 는 낙관적이었다. MI 계산 비용만 셌고, 폴드마다
전처리가 40컬럼이 아니라 200컬럼을 처리하게 되는 비용을 빼먹었기 때문이다.

**다만 비용은 후보 피처 수에 전적으로 달려 있다.** demo 데이터(88후보, top_k 없음)에서는
선별 ON 으로 전 모델이 정상 완주했고 추가비용이 눈에 띄지 않았다.

**폴드 간 Jaccard 중복도**

| 조건 | Jaccard | 의미 |
|---|---|---|
| demo, 88후보, top_k 없음 | **1.000** | 폴드마다 같은 피처를 고름. 폴드 밖 선별을 써도 무방했던 경우 |
| 합성, 200후보 → top_k 40 | **0.265** | 폴드마다 다른 피처를 고름. 폴드 밖 선별이었다면 CV 점수가 낙관 편향 |

Jaccard 는 그 자체가 진단 지표다. 1.0 에 가까우면 선별이 안정적이라 폴드 밖에서 해도
결과가 같고, 낮으면 "어떤 피처가 중요한가"라는 질문의 답이 구간마다 달라진다는 뜻이므로
SHAP 해석까지 함께 조심해야 한다. 학습 화면 "폴드 내부 선별 안정성" 패널에 표시된다.
